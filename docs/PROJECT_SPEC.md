# AgentOps Project Specification

## 1. Product definition

AgentOps is an evidence-driven microservice incident diagnosis and controlled recovery platform aimed at demonstrating AI-agent and Python-backend engineering. It aggregates operational signals, produces bounded and reviewable hypotheses, and safely coordinates recovery without granting an LLM execution authority.

### Objectives

1. Reduce incident diagnosis time.
2. Increase completeness and traceability of root-cause evidence.
3. Reduce risk from automated recovery.
4. Make every decision, model call, tool call, approval, action, verification, and rollback observable, explainable, and auditable.

### Success is measured, not asserted

All quality, latency, safety, recovery, scale, token, and cost claims must be generated by a reproducible versioned evaluation. The project must explicitly report hardware, dataset version, model/prompt version, concurrency, sample count, and confidence intervals or raw distributions as appropriate.

## 2. Actors and access

| Role | Capabilities |
| --- | --- |
| Viewer | Read incidents, evidence, timelines, reports, and audit events. |
| Operator | Start/cancel investigation, request remediation, and execute approved operations within policy. |
| Approver | Review, approve, reject, or let expire policy-eligible recovery plans; cannot bypass policy. |
| Admin | Manage users, roles, policies, prompts, tools, and retention; remains subject to audit and non-bypassable safety invariants. |

Separation of duties is configurable but must be enforced for medium/high-risk actions in the reference deployment: the proposer/operator cannot be the sole approver.

## 3. Components

### Decision agents

- **Diagnosis Agent** receives a typed, budgeted context. It produces a finite investigation plan, calls only read-only tools through the Tool Gateway, and returns ranked root-cause candidates with evidence IDs, counter-evidence, missing evidence, and uncertainty.
- **Remediation Agent** runs only for candidates accepted by the Evidence Gate. It emits a typed recovery proposal containing prerequisites, exact allowed action, risk assumptions, verification criteria, and rollback plan.

### Deterministic components

Alert deduplicator/merger, Triage, collectors, Evidence normalizer/validator/store, Evidence Gate, Context Builder preprocessing, Tool Gateway, Policy Engine, Approval service, Action Executor, Health Verifier, Rollback Controller, incident state machine, audit ledger, checkpoint/work queue, and Ground Truth evaluator are ordinary deterministic services/modules.

### Constrained postmortem node

After closure, a constrained LLM node may draft a postmortem from confirmed facts and resolvable evidence references. Humans can revise it; revisions and source references are versioned and audited. It is not a team of writing agents.

## 4. End-to-end flow

1. Accept an alert and deterministically deduplicate/merge it into an incident.
2. Triage severity and load service topology plus bounded baseline context.
3. The Diagnosis Agent emits a finite typed investigation plan.
4. Independent read-only tool steps run in parallel through the Tool Gateway.
5. Results are normalized, hashed, quality-scored, versioned, and persisted as Evidence and Artifacts.
6. The agent produces root-cause candidates with supporting and contradicting evidence references.
7. The deterministic Evidence Gate validates evidence existence, incident ownership, freshness, source independence, and treatment of counter-evidence.
8. If insufficient, use a bounded replan budget; otherwise transfer to a human with the missing-evidence explanation.
9. The Remediation Agent produces a structured plan only for a gate-approved root cause.
10. Schema validation and Policy Engine decide whether the plan is forbidden, auto-eligible, or approval-required. The reference `rollback_service` action is approval-required.
11. LangGraph Interrupt persists a checkpoint while medium/high-risk action awaits non-expired approval.
12. The Executor acquires an action lock and executes idempotently through the versioned write tool.
13. Health Verifier observes real metrics, health endpoint, running version, new alerts, and a stable window.
14. On success, close the incident. On verification failure, perform an idempotent rollback when allowed, or re-diagnose within budget. Rollback failure transfers to a human.
15. Generate an evidence-linked postmortem from confirmed facts.

## 5. Incident lifecycle

Initial states and allowed transitions (final names may be refined in an ADR before schema implementation):

```text
DETECTED -> TRIAGED -> INVESTIGATING -> EVIDENCE_REVIEW
EVIDENCE_REVIEW -> INVESTIGATING             (bounded replan)
EVIDENCE_REVIEW -> NEEDS_HUMAN               (insufficient evidence/budget)
EVIDENCE_REVIEW -> PLANNING_REMEDIATION
PLANNING_REMEDIATION -> POLICY_REVIEW
POLICY_REVIEW -> REJECTED | AWAITING_APPROVAL | READY_TO_EXECUTE
AWAITING_APPROVAL -> REJECTED | EXPIRED | READY_TO_EXECUTE
READY_TO_EXECUTE -> EXECUTING -> VERIFYING
VERIFYING -> RESOLVED | ROLLING_BACK | INVESTIGATING
ROLLING_BACK -> ROLLED_BACK | NEEDS_HUMAN
RESOLVED -> CLOSED
```

Cancellation is legal only from explicitly enumerated non-terminal states. Every transition records actor, reason, correlation/causation IDs, prior/new state, and timestamp. Database constraints and transition tests prevent illegal jumps.

## 6. Evidence contract

Each Evidence record includes at minimum:

- immutable Evidence ID and owning Incident ID;
- source type and source instance;
- tool/schema version and exact normalized query parameters;
- timezone-aware observation/query time range and collection time;
- content hash and Artifact reference rather than oversized inline payload;
- parser/normalizer version, quality score/reasons, and expiration status;
- lineage to the tool call, workflow run, and redaction transform;
- trust classification and prompt-injection flags.

The Evidence Gate rejects absent, cross-incident, stale, unverifiable, or fabricated references. It evaluates source independence and unresolved counter-evidence using versioned deterministic rules. A numeric model confidence is metadata only and cannot make the gate pass.

## 7. Tool Gateway contract

Every tool has a versioned input/output schema, read/write classification, risk tier, required RBAC permissions, timeout, bounded retry policy, idempotency behavior, audit behavior, and enabled version range.

Read tools:

- `query_metrics`
- `query_logs`
- `query_traces`
- `query_deployments`
- `get_service_topology`
- `search_similar_incidents`

The first write tool is a strict allowlisted `rollback_service`. It requires Incident ID, Approval ID, and Idempotency Key. It accepts no free-form command or arbitrary target. Old similar incidents are clearly labeled historical references and never promoted to current-incident facts.

## 8. Context construction

Context Builder clusters and deduplicates log error patterns, summarizes metric trends without hiding raw Artifact references, extracts trace critical paths, highlights deployment changes, applies token budgets, preserves provenance labels, redacts sensitive values, and quarantines untrusted prompt-like log content. Truncation decisions are recorded so missing context is explainable.

## 9. Workflow durability and memory

LangGraph supplies typed state, conditional routing, parallel read-only investigation, finite loops and replanning, PostgreSQL checkpoints, human interrupts, pause/resume/cancel, worker-crash continuation, and verification-failure routing. Working memory lives in workflow state/checkpoints. Incident experience is persisted separately and indexed with pgvector for similar-incident lookup; retrieved incidents are advisory only.

API and worker processes are separate. Workers claim jobs through PostgreSQL using transactional claiming, leases, heartbeats, attempt limits, and stale-lease recovery. Concurrency limits and load tests are required; no production-scale claim is allowed without data.

The MVP control plane does not use Kafka, NATS, or Redis for queuing/caching. Redis is present only inside the diagnosed simulator. A control-plane broker or cache requires measured need (for example broadcast, distributed rate limiting, or demonstrated PostgreSQL queue limits) and a superseding ADR.

## 10. Prompt lifecycle

Prompt Registry entries contain Prompt ID, semantic version, immutable content fingerprint, model/provider parameters, compatible schemas, trace linkage, evaluation result, status, and rollback predecessor. Promotion requires regression gates. Runtime traces identify the exact prompt/model/settings used.

## 11. Execution and verification

Policy consumes actor, incident, evidence-gate result, proposal, tool metadata, environment, and risk. It produces a versioned decision with reasons. Approval binds the immutable proposal fingerprint, expires, and is invalidated by any material modification.

Executor accepts typed commands only, verifies policy and approval again, acquires an execution lock, enforces idempotency/replay protection, records before/after snapshots, times out safely, and writes append-only audit events.

Health verification is deterministic and scenario-aware. It checks error rate, P95 latency, health endpoint, running service version, new alerts, and a stability observation window. Failure triggers an idempotent rollback where permitted; rollback failure becomes `NEEDS_HUMAN`.

## 12. Simulator and Ground Truth

Docker Compose must run API Gateway, Order Service, Inventory Service, Payment Service, PostgreSQL, Redis, Prometheus, Loki, Tempo, and OpenTelemetry Collector.

Each reproducible scenario owns an isolated Ground Truth manifest with actual root cause, symptoms, decisive metrics/logs/traces, deployment change, recommended action, validation conditions, and rollback conditions:

1. new release causes HTTP 500;
2. database connection pool exhaustion;
3. Redis timeout;
4. downstream service high latency;
5. memory leak;
6. bad configuration.

Ground Truth is mounted/read only by evaluation processes, never the platform API/worker or model context path. Tests must prove this separation.

## 13. Administration console

The initial console provides incident list/detail, workflow timeline, investigation plan, evidence/artifact viewer, root-cause support and counter-evidence, approval center, execution before/after signals, trace view, token/cost view, and audit status. The UI is not a second source of authorization; backend policy and state transitions remain authoritative.

## 14. Observability

Two layers are mandatory:

- **Diagnosed system:** metrics, logs, traces, deployments, topology, and alerts.
- **Agent platform:** workflow nodes, model calls, prompt versions, tool calls, evidence gates, approvals, checkpoints, job leases, executions, verifications, rollbacks, tokens, latency, and cost.

All layers share correlation identifiers while preventing sensitive payload leakage.

## 15. Delivery constraints and non-goals

Core version exclusions: A2A; a general-purpose Agent Harness; multi-agent writing; collector agents; arbitrary shell agents; real production Kubernetes control; Kafka/NATS; multiple agent frameworks; general document Q&A; and core-path MCP conversion. MCP may later be a read-only adapter. A2A is considered only after a real independently deployed agent-service boundary exists.

## 16. Definition of done

A capability is done only when its schemas and invariants are documented, implementation is typed, authorization/audit behavior is present, relevant negative and recovery paths are tested, observability is emitted, documentation/TODO are updated, and required checks pass in a reproducible environment.
