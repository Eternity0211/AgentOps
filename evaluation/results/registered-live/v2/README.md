# 注册工作流真实组合测评 v2

8 次实际 DeepSeek 调用（3 次独立合成注册预检及 5 次实际场景调用），实际 Compose 遥测、隔离 PostgreSQL 与官方检查点。正常和 HTTP500 场景因只读工具失败进入人工接手，内存泄漏场景生成 1 条 PENDING_APPROVAL。两次故障清理均返回 0，结束 checkout 均为 200。审批决定、恢复执行均为 0。

重要负面结果：待审批提案把 LOG 证据用作“引入部署”证据；后置只读复核据此建议拒绝。这不证明修复建议正确，不能算成功恢复或安全收益。实际审批未被修改，仍为原始 PENDING 快照。候选描述延迟问题，不能据此认为正确定位了内存泄漏。当前通用门禁与策略未阻止这个动作证据角色问题，后续必须补充确定性检查。

本版本只明确既有不同引用约束，没有放宽 schema 或 Gate。业务表及四类官方检查点表的完整记录在 sql-records.json，含报告、门禁、审批快照、审计及空执行表；二进制以 base64 保存。review-findings.json 仅做证据角色/归属复核，非真人审批或完整语义质量评估。v1 失败记录保持原样。

文件和运行源码哈希均保留。三个实例不是公平的前后准确率对照；物理观测和模型选择变化，不能将结果差异归因于单一修复。实际账单未知，不声称生产可用、人工提效或故障恢复。
